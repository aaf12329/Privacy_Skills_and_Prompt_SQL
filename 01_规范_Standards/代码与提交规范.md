| # | GitHub 仓库 | 本地目录 | 可见性 | 备注 |
|:-:|---|---|:-:|---|
| 1 | `<repo-a>` | `<Desktop/repo-a>` | 🔒 私有 | 主项目，成文规范所在地 |
| 2 | `<repo-b>` | `<Desktop/repo-b>` | 🌍 **公开** | 提交信息按对外标准写 |
| 3 | `<repo-c>` | `<Desktop/repo-c>` | 🔒 私有 | 实验仓库 |
| 4 | —（无 remote） | `<Desktop/repo-d>` | ⚠️ **未推送** | 纯本地，**最该先备份** |

**维护要点**：可见性列决定提交信息的口径；发现"无 remote"的仓库立即升级为 P0 备份项。

## 02 · Git 分工

两种成熟方案，选一种作为默认并写明（规则在演进，**以最新的为准**）：

**方案一 · AI 提交** 🟡（推荐默认）
- 日常 `git add` + `git commit` 由 AI 执行；
- 🔴 `git push` 只有所有者本人执行——AI 需要 push 必须先征得同意。

**方案二 · 指令块审查** 🟡
- AI 把 add/commit/push 整理成可粘贴的命令块，所有者审查后自己执行；
- 例外：所有者明确说"你 push 一下"时直接执行——默认是**等审查**，不是**拒绝推**。

> 演进记录写成 `日期 ──▶ 方案 ──▶ 一句话变化`；旧方案标注"已被取代的部分"，
> 仍有效的条目（先声明、代码带注释、README 同步）单独保留。

## 03 · 提交信息

> **核心原则**：中英双语、中文在前；一段话说清：做了什么 + 怎么验证的 + 影响哪些文档。

**格式 A · 单行双语式** 🟡（轻量仓库，`CH:` / `EN:` 各一行）

```text
CH:新增配置导出功能（默认关闭），README 同步更新
EN:Add config export (off by default); README updated accordingly
```

**格式 B · 段落式** ⭐ 推荐（新提交向此格式靠拢）：标题 + 中英两组 bullets。

```text
功能：数据管道断点续跑 + 进度落盘

- 每个 stage 完成后写 checkpoint.json，中断后跳过已完成阶段
- 抽样验证：3 次中断重启，结果与一次跑完一致
- README 工作流一节同步更新

Feature: resumable data pipeline with progress on disk

- checkpoint.json written after each stage; restarts skip finished stages
- Verified by 3 interrupt-restart runs, output identical to a single run
- README workflow section updated
```

**格式 C · 序号式** 🟢、**格式 D · 竖线分隔式** 🟢：分别适合教学/刷题仓库与
标题一行中英竖线分隔（正文两个 `-m` 分写）——两种备选，按需取用。

**类型前缀** 🟡：`文档：`　`规范：`　`功能：`　`修复：`　`整理：`　`重构：`
**特殊约定** 🟡：`历史版本：` 前缀 = 旧代码快照存档；tag 命名 `v主.次` / `功能词-v1`。
**历史教训** 🟡：标题 ≤72 字符（细节放正文）；前缀大小写统一；多仓库风格向格式 B 收敛。

## 04 · 提交前检查清单

> **每次 commit 前逐项过，适用于所有仓库**；方括号按项目实际裁剪：

- [ ] 1️⃣ 本次改动的**功能/脚本/数据**，已在 README 的架构树与进度表里反映？
- [ ] 2️⃣ 引入了**新的文件类型或目录**？→ `.gitignore` 增补或加白名单例外
- [ ] 3️⃣ 新增了**指令或脚本**？→ `<COMMANDS.md 或等价的指令文档>` 同步
- [ ] 4️⃣ 触发了**磁盘策略条款**（≥1GB 写入/删除、跨盘、环境安装）？→ `<台账文件>` 登记
- [ ] 5️⃣ 有了**新的实测结果或图表**？→ `<docs/ 或等价的归档目录>` 存档

## 05 · 代码工作流程

```
① 先声明 ──▶ ② 代码带注释 ──▶ ③ README 同步 ──▶ ④ git 提交
   说清做什么/为什么   关键逻辑写注释      中英双语同时改     按 §02 分工
   （拍板后再动）      与 git 历史互补                          push 归所有者 🔴
```

> 🟡 README 是项目状态的**唯一权威来源**——"已知问题"过期会让完成的重构看起来没做完。

## 07 · 仓库卫生

### 🔴 永不入库

- 密钥与凭据（`.env`、API key）
- 虚拟环境（`myvenv/`、`venv/`、`.conda/`）
- 缓存与生成物（`__pycache__/`、构建输出）、`node_modules/`
- 硬件照片等临时资料
- **数据文件**——聊天记录、数据集原始文件（教训：某历史存档仓库把聊天记录
  入库，单几次提交 **+43 万行**）

### 🔴 身份信息过滤（提交与文件内容）

- **提交信息与提交的文件内容中过滤所有者身份信息**——真实姓名、学校/单位、
  地理位置、联系方式、健康状况等；
- 确需写入时**先征得所有者同意**（默认按"不写"处理）；
- 同理适用于：对外分享的文档、截图、日志、演示材料；
- 例外：所有者明确要求写入的内容（如项目署名、致谢）。

**Filter identity info out of commits and repos** — real name, school/employer,
location, contact, health status — in both commit messages and committed file
contents; ask the owner first if it seems necessary. Applies to shared docs,
screenshots and logs too.

### 🟡 过滤标记约定（非通用文件）

- 仓库中若混入**非通用文件**（如个人画像、私有偏好），在文件顶部加一行
  **【请过滤本文件】** 标记；
- 该标记的含义：分享仓库、批量处理、生成公开内容时**跳过此文件**；
- **正式使用该文件时，删除这一行标记**。

**Filter-marker convention** — mark non-generic files (personal profiles, private
preferences) with a 【请过滤本文件】 line at the top: skip them when sharing,
bulk-processing or publishing; delete the marker line before real use.

### 🟡 选择性入库（大文件）

| 入库 ✅ | 不入库 ❌ |
|---|---|
| 交付性产物（克隆即用的最终权重/成品，单个几 MB 级） | 训练原始输出（`runs/`、checkpoint）——README 记路径即可 |

### 🟡 磁盘报备制度

- ≥1GB 写入/删除、跨盘操作、环境安装 → 台账文件登记；
- 大动作前后**强制检查系统盘剩余容量**，报备时带数字，执行后复测记差额；
- 超大数据集放**非系统盘**的专用数据目录（连压缩包），小数据留在仓库旁。

## 09 · 常见遗留问题

> 自查模板：逐条对照自己的仓库。

| 优先级 | 问题形态 | 说明 |
|:-:|---|---|
| **P0** | ⚠️ 有 commit 但无 remote | 硬盘一坏全没，**最该先推** |
| P1 | 🌍 公开仓库的提交信息泄露内部描述 | 公开仓库按对外标准写 |
| P1 | 数据膨胀 | 已入库的原始数据迁出 + `.gitignore` 阻止继续增长 |
| P2 | 多套提交格式并存 | 新仓库统一格式 B，旧的不追溯 |

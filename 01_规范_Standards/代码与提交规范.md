## 02 · Git 分工规则

规则在演进，**以最新的为准**。两种成熟方案，选一种作为默认并写明：

### 方案一 · AI 提交 🟡（推荐默认）

- 日常 `git add` + `git commit` **由 AI 助手负责执行**；
- 🔴 **`git push` 只有仓库所有者本人执行**——助手需要 push 必须**先征得同意**，
  除非所有者明确说过可以推。

### 方案二 · 指令块审查 🟡

- 助手把 `git add` / `git commit` / `git push` 整理成**可直接粘贴的命令块**，
  所有者审查后自己执行（"准备好指令我看完就 push"）；
- **例外**：所有者明确说"你 push 一下"时助手直接执行——默认是**等审查**，
  不是**拒绝推**。

> 演进记录这样写：`日期 ──▶ 方案 ──▶ 一句话变化`，旧方案标注"已被取代的部分"，
> 仍然有效的条目（先声明、代码带注释、README 同步）单独点名保留。

## 03 · 提交信息规范

> ### 核心原则
> **中英双语，中文在前。** 一段话说清：做了什么 + 怎么验证的 + 影响哪些文档。

### 格式 A · 单行双语式 🟡

适用：轻量仓库。`CH:` / `EN:` 前缀，各一行。

```text
CH:新增配置导出功能（默认关闭），README 同步更新
EN:Add config export (off by default); README updated accordingly
```

### 格式 B · 段落式 ⭐ 推荐

标题 + 中英两组 bullets，信息最完整，**新提交向此格式靠拢**。

```text
功能：数据管道断点续跑 + 进度落盘

- 每个 stage 完成后写 checkpoint.json，中断后跳过已完成阶段
- 抽样验证：3 次中断重启，结果与一次跑完一致
- README 工作流一节同步更新

Feature: resumable data pipeline with progress on disk

- checkpoint.json written after each stage; restarts skip finished stages
- Verified by 3 interrupt-restart runs, output identical to a single run
- README workflow section updated
```

### 格式 C · 序号式 🟢

适合教学/刷题仓库：两位数字递增，一个模型/主题一个 commit。

```text
01 线性回归：手推梯度 + 数值梯度检查，GD 收敛到 w=2.98 b=0.98
```

### 格式 D · 竖线分隔式 🟢

标题一行中英竖线分隔，正文两个 `-m` 分写中英：

```bash
git commit -m "新增 LightGBM 对比实验 | Add LightGBM comparison experiments" \
           -m "<中文正文>" -m "<English body>"
```

### 类型前缀 🟡

内容超出"阶段"范畴时，标题以类型词开头：

`文档：`　`规范：`　`功能：`　`修复：`　`整理：`　`重构：`

### 特殊约定

- 🟡 **`历史版本：` 前缀** = 旧代码快照存档，表示"历史文件入库，不是新功能"；
- 🟡 **tag 命名**：`v主.次` / `v主.次-变体` / `功能词-v1`——实例：`v0.1` `v1.5-qqbot` `gui-v1`。

### 已知的毛病 🟡 下次改

| 毛病 | 后果 | 改法 |
|---|---|---|
| 单行标题拖到 200~400 字符 | `git log --oneline` 不可读 | 标题 ≤ ~72 字符，细节放正文 |
| `CH:` / `Ch:` 大小写混用 | 观感不统一 | 统一 `CH:` |
| 多个仓库多套格式 | 历史风格割裂 | 新提交统一向格式 B 靠拢，旧的不追溯 |

## 04 · 提交前检查清单

> **每次 commit 前逐项过，适用于所有仓库**；方括号按项目实际裁剪：

- [ ] 1️⃣ 本次改动涉及的**功能/脚本/数据**，已在 README 的架构树与进度表里反映？
- [ ] 2️⃣ 引入了**新的文件类型或目录**？→ `.gitignore` 增补或加白名单例外
- [ ] 3️⃣ 新增了**指令或脚本**？→ `<COMMANDS.md 或等价的指令文档>` 同步
- [ ] 4️⃣ 触发了**磁盘策略条款**（≥1GB 写入/删除、跨盘、环境安装）？→ `<log.md 或等价的台账>` 登记
- [ ] 5️⃣ 有了**新的实测结果或图表**？→ `<docs/ 或等价的归档目录>` 存档

## 05 · 代码工作流程

```
① 先声明 ──▶ ② 代码带注释 ──▶ ③ README 同步 ──▶ ④ git 提交
  动手前说清楚     关键逻辑写注释      中英双语同时改       按第 02 节分工
  做什么、为什么    与 git 历史互为     API表/Roadmap/      push 红线归所有者 🔴
  （拍板后再动）   补充                结构树
```

> 🟡 README 是项目状态的**唯一权威来源**——新的协作者（或评审者）看的第一份
> 材料，"已知问题"过期会让完成的重构看起来没做完。

## 06 · 分支与标签

| 事项 | 规则 |
|---|---|
| 分支 | 🟡 **只用 `main`**，直推；不开 feature 分支，不用 PR / merge（单人多机工作流现状） |
| 将来需要分支 | 按 `阶段/内容` 命名，合回 main 后删除 |
| 标签 | 见 03 节特殊约定；除特殊仓库外暂不用 tag |

## 07 · 仓库卫生

### 🔴 永不入库

- 密钥与凭据（`.env`、API key）
- 虚拟环境（`myvenv/`、`venv/`、`.conda/`）
- 缓存与生成物（`__pycache__/`、构建输出）、`node_modules/`
- 硬件照片等临时资料
- **数据文件**——聊天记录、数据集原始文件（教训：某历史存档仓库把聊天记录
  入库，单几次提交 **+43 万行**）

### 🟡 选择性入库（大文件）

| 入库 ✅ | 不入库 ❌ |
|---|---|
| 交付性产物（克隆即用的最终权重/成品，单个几 MB 级） | 训练原始输出（`runs/`、checkpoint）——README 记路径即可 |

### 🟡 磁盘报备制度

- ≥1GB 写入/删除、跨盘操作、环境安装 → 台账文件登记；
- 大动作前后**强制检查系统盘剩余容量**，报备时带数字，执行后复测记差额；
- 超大数据集放**非系统盘**的专用数据目录（连压缩包），小数据留在仓库旁。

## 09 · 常见遗留问题

> 自查模板：以下是从真实仓库蒸馏出的典型问题形态，逐条对照自己的仓库：

| 优先级 | 问题形态 | 说明 |
|:-:|---|---|
| **P0** | ⚠️ 有 commit 但无 remote | 纯本地仓库硬盘一坏全没，**最该先推** |
| P1 | 🌍 公开仓库的提交信息泄露内部描述 | "还没测试""外包给某工具"这类话会被陌生人看到，公开仓库按对外标准写 |
| P1 | 数据膨胀 | 已入库的聊天记录/原始数据考虑迁出 + `.gitignore` 阻止继续增长 |
| P2 | 多套提交格式并存 | 新仓库统一格式 B，旧仓库不追溯 |

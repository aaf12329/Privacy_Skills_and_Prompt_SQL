给**所有**仓库建一张总览表放在这里，AI 读完即知全貌、不再逐个探索：

| # | GitHub 仓库 | 本地目录 | 可见性 | 备注 |
|:-:|---|---|:-:|---|

## 02 · Git 分工

两种成熟方案，选一种作为默认并写明（规则在演进，**以最新的为准**）：

**方案一 · AI 提交** 🟡（推荐默认）
- 日常 `git add` + `git commit` 由 AI 执行；
- 🔴 `git push` 只有所有者本人执行——AI 需要 push 必须先征得同意。

**方案二 · 指令块审查** 🟡
- AI 把 add/commit/push 整理成可粘贴的命令块，所有者审查后自己执行；
- 例外：所有者明确说"你 push 一下"时直接执行——默认是**等审查**，不是**拒绝推**。

> 演进记录写成 `日期 ──▶ 方案 ──▶ 一句话变化`；旧方案标注"已被取代的部分"，
> 仍有效的条目（先声明、代码带注释、README 同步）单独保留。

## 03 · 提交信息

> **核心原则**：中英双语、中文在前；一段话说清：做了什么 + 怎么验证的 + 影响哪些文档。

**格式 A · 单行双语式** 🟡（轻量仓库，`CH:` / `EN:` 各一行）

```text
CH:新增配置导出功能（默认关闭），README 同步更新
EN:Add config export (off by default); README updated accordingly
```

**格式 B · 段落式** ⭐ 推荐（新提交向此格式靠拢）：标题 + 中英两组 bullets。

```text
功能：数据管道断点续跑 + 进度落盘

- 每个 stage 完成后写 checkpoint.json，中断后跳过已完成阶段
- 抽样验证：3 次中断重启，结果与一次跑完一致
- README 工作流一节同步更新

Feature: resumable data pipeline with progress on disk

- checkpoint.json written after each stage; restarts skip finished stages
- Verified by 3 interrupt-restart runs, output identical to a single run
- README workflow section updated
```

**格式 C · 序号式** 🟢、**格式 D · 竖线分隔式** 🟢：分别适合教学/刷题仓库与
标题一行中英竖线分隔（正文两个 `-m` 分写）——两种备选，按需取用。

**类型前缀** 🟡：`文档：`　`规范：`　`功能：`　`修复：`　`整理：`　`重构：`
**特殊约定** 🟡：`历史版本：` 前缀 = 旧代码快照存档；tag 命名 `v主.次` / `功能词-v1`。
**历史教训** 🟡：标题 ≤72 字符（细节放正文）；前缀大小写统一；多仓库风格向格式 B 收敛。

## 04 · 提交前检查清单

> **每次 commit 前逐项过，适用于所有仓库**；方括号按项目实际裁剪：

- [ ] 1️⃣ 本次改动的**功能/脚本/数据**，已在 README 的架构树与进度表里反映？
- [ ] 2️⃣ 引入了**新的文件类型或目录**？→ `.gitignore` 增补或加白名单例外
- [ ] 3️⃣ 新增了**指令或脚本**？→ `<COMMANDS.md 或等价的指令文档>` 同步
- [ ] 4️⃣ 触发了**磁盘策略条款**（≥1GB 写入/删除、跨盘、环境安装）？→ `<台账文件>` 登记
- [ ] 5️⃣ 有了**新的实测结果或图表**？→ `<docs/ 或等价的归档目录>` 存档

## 07 · 仓库卫生

### 🔴 永不入库

- 密钥与凭据（`.env`、API key）
- 虚拟环境（`myvenv/`、`venv/`、`.conda/`）
- 缓存与生成物（`__pycache__/`、构建输出）、`node_modules/`
- 硬件照片等临时资料
- **数据文件**——聊天记录、数据集原始文件（教训：某历史存档仓库把聊天记录
  入库，单几次提交 **+43 万行**）

### 🔴 身份信息过滤（提交与文件内容）

- **提交信息与提交的文件内容中过滤所有者身份信息**——真实姓名、学校/单位、
  地理位置、联系方式、健康状况等；
- 确需写入时**先征得所有者同意**（默认按"不写"处理）；
- 同理适用于：对外分享的文档、截图、日志、演示材料；
- 例外：所有者明确要求写入的内容（如项目署名、致谢）。

**Filter identity info out of commits and repos** — real name, school/employer,
location, contact, health status — in both commit messages and committed file
contents; ask the owner first if it seems necessary. Applies to shared docs,
screenshots and logs too.

### 🟡 过滤标记约定（非通用文件）

- 仓库中若混入**非通用文件**（如个人画像、私有偏好），在文件顶部加一行
  **【请过滤本文件】** 标记；
- 该标记的含义：分享仓库、批量处理、生成公开内容时**跳过此文件**；
- **正式使用该文件时，删除这一行标记**。

**Filter-marker convention** — mark non-generic files (personal profiles, private
preferences) with a 【请过滤本文件】 line at the top: skip them when sharing,
bulk-processing or publishing; delete the marker line before real use.

### 🟡 选择性入库（大文件）

| 入库 ✅ | 不入库 ❌ |
|---|---|
| 交付性产物（克隆即用的最终权重/成品，单个几 MB 级） | 训练原始输出（`runs/`、checkpoint）——README 记路径即可 |

### 🟡 磁盘报备制度

- ≥1GB 写入/删除、跨盘操作、环境安装 → 台账文件登记；
- 大动作前后**强制检查系统盘剩余容量**，报备时带数字，执行后复测记差额；
- 超大数据集放**非系统盘**的专用数据目录（连压缩包），小数据留在仓库旁。

## 09 · 常见遗留问题

> 自查模板：逐条对照自己的仓库。

| 优先级 | 问题形态 | 说明 |
|:-:|---|---|
| **P0** | ⚠️ 有 commit 但无 remote | 硬盘一坏全没，**最该先推** |
| P1 | 🌍 公开仓库的提交信息泄露内部描述 | 公开仓库按对外标准写 |
| P1 | 数据膨胀 | 已入库的原始数据迁出 + `.gitignore` 阻止继续增长 |
| P2 | 多套提交格式并存 | 新仓库统一格式 B，旧的不追溯 |

## 10 · 文件删除与回收站

- 🔴 **删除项目文件夹之外的任何东西，必须先报备**——对话里说清楚要删什么、
  为什么删，得到确认后再动手；"先整理进知识库/仓库，再删原件"是推荐顺序。
- 🔴 **永不清空回收站**——删除一律**送回收站**，给误删留后路：
  ```powershell
  # PowerShell 送回收站（Git Bash 里 rm 是永久删除，项目文件夹之外禁止直接 rm）
  Add-Type -AssemblyName Microsoft.VisualBasic
  [Microsoft.VisualBasic.FileIO.FileSystem]::DeleteFile($path, 'OnlyErrorDialogs', 'SendToRecycleBin')
  [Microsoft.VisualBasic.FileIO.FileSystem]::DeleteDirectory($dir, 'OnlyErrorDialogs', 'SendToRecycleBin')
  ```
- 🟡 删除前快速核对：目标内容是否已有归宿（并入知识库 / 仓库另有副本 / 任务产物已交付）。

**Never delete outside a project folder without reporting first** (say what and why,
get confirmation), and **never empty the Recycle Bin** — always send deletions to the
Recycle Bin (`SendToRecycleBin`), never bare `rm` outside project folders.

## 01 · 分层与解耦铁律

```
入口层（壳）      控制台入口 / 图形入口 / 循环调度     ← 全项目唯一有权"横向调用"的层
    │
功能层（模块目录） 各业务模块（I/O、适配、算法、检索…）
    │
共用层（common）  路径地址簿 / 设备 / 绘图 / 通用工具   ← 人人读它，它不调用任何人
    │
标准库 / 第三方
```

- 🔴 **功能层模块之间零 import**——需要共享逻辑就**下沉到共用层**；要协作由入口层编排。
  （唯一例外：一个显式的"适配 / 聚合"模块，须在文件头注明它是特批的横向层。）
- 🔴 **所有文件位置一律从路径地址簿拿**（见第 02 节），严禁各文件自己拼路径。
- 🟡 依赖方向单向向下：入口 → 功能 → 共用 → 标准库；**禁止反向 import 与循环依赖**。
- 🟡 判断标准：画出调用图，应是**树**——若出现横向连线，就是该解耦的地方。

## 02 · 路径地址簿（Store 模式）

- 🔴 全项目的文件 / 目录位置集中登记在**一个路径模块**里（纯常量，不做读写）；
- 🔴 **地址簿只被读、不调用任何人**；新增产物（索引、缓存、导出文件）先登记再使用；
- 🟡 好处：改目录结构只改一处；测试可整体把路径重定向到临时目录（见第 08 节）。

## 03 · 重复的判定与消除（重构操作规程）

- 🔴 **判定**：同一段逻辑出现 ≥2 处 = 重复；出现"改一处要同步 N 处" = 已欠债，尽快还清。
- 🔴 **消除顺序**：① 抽到共用层 → ② 逐文件删本地副本 → ③ 改为 `import` →
  ④ 调用点传参（各文件保留自己的参数常量）。
- 🔴 **重构前先备份、重构后基线对比**：测试通过数不得低于重构前；
  再做运行时冒烟（能 import、能调用、不改输入）。
- 🟡 **批量重构操作要点**（血泪教训，可直接照做）：
  - 用 **AST 定位**重复块（函数 / 赋值）比肉眼可靠：`ast.parse` 取 `lineno / end_lineno`；
  - **先按原文件行号删块，再做文本替换**——替换会改变行数，替换后再按旧行号删会删错行；
  - 文本插入代码块时**每行都要带换行符**，否则会与前一行粘连成语法错误；
  - 注解赋值（`x: dict = {}`）在 AST 里是 `AnnAssign` 而非 `Assign`，扫漏会留下死代码；
  - 改完**三件套缺一不可**：全部受影响文件 `ast.parse` + 跑测试套件 + 运行时冒烟。

## 04 · I/O 单一入口

- 🔴 同类 I/O 只开**一个口子**：文本读写走同一个函数（自带编码回退），
  结构化数据（JSON 等）单独一个口子，**不开第三处**；
- 🟡 好处：编码 / 换行 / 原子写这些问题只解决一次；要加日志或审计只改一个地方。

## 05 · 返回契约（接口稳定）

- 🔴 一个模块对外**只返回约定的形状**（统一 dict / 数据类），调用方按契约解包；
  字段名一旦发布就不改（要扩展就加新字段，不改旧字段语义）。
- 🟡 契约写进模块文件头的 docstring；改契约 = 一次明确的提交（含所有调用点同步）。

## 06 · 错误处理哲学

- 🔴 **给"能修正的人"可操作的提示**：面向模型的错误转成带正确示例的文本
  （自动重试 / 自我修正的命脉）；面向人的错误写清"怎么排查"（含下一个动作）。
- 🔴 **只重试暂时性错误**（429 / 超时 / 5xx，指数退避 + 抖动）；
  4xx 与逻辑错误立刻暴露——重试只会掩盖问题。
- 🟡 单轮失败不退出主循环——每一层都兜住自己的异常。

## 07 · 安全三闸门

| 闸门 | 做法 |
|---|---|
| 路径沙箱 | 真实路径解析 + 限定项目根 + 敏感文件黑名单（`.env` / 私钥） |
| 危险操作审批 | 三态：`ask` / `auto` / `never`；无交互环境（后台线程 / 服务）禁止阻塞式输入 |
| 密钥管理 | 🔴 密钥只进 `.env`，严禁硬编码（教训：明文 key 差点随分享泄露） |

## 08 · 自测规范

- 🟡 每个模块文件底部带 `if __name__ == "__main__":` 自测块（跑一下就知道没坏）；
- 🔴 自测**不碰真实数据**：路径重定向到临时目录；
- 🔴 涉网络 / 涉付费接口的自测用**假实现替换**（假模型 / 假响应），零花费；
- 🟡 替换后仍不生效时，检查是否有注册表 / 字典**持有旧函数引用**（踩过的坑）；
- 🟡 GUI / 长任务验证不只看"进程活着"，要断言**具体状态**（像素尺寸、行数、字段值）。

## 09 · 注释与命名

- 🟡 文件头写**函数结构树**（分区导航）+ 调用关系总览；函数一行 docstring 说清
  "干什么 / 被谁调用"；行内注释只写"代码看不出来的"（约束、坑、为什么这样做）；
- 🟡 重构时**对外名字能不变就不变**（向后兼容）；
- 🟡 给第三方开源代码加注时，头部标注"结构分析注释 · 非原作者所写"。

## 10 · LLM / Agent 类项目的追加契约

> 面向"调用大模型 + 工具循环"这一**类**项目（非单一项目）。

**模型适配层返回契约**（多家厂商统一成一个形状）：

```python
{"content": str, "reasoning": str, "usage": usage|None, "tool_calls": list}
```

- 🟡 `arguments` 从 API 拿到时是 **JSON 字符串**，不是对象——先 `json.loads`；
- 🟡 `usage.completion_tokens` 通常**已含** reasoning tokens，统计成本别二次相加。

**工具消息契约**（违反任何一条都可能被 API 拒绝）：

1. 🔴 assistant 消息必须**原样回存**（含 tool_calls 字段）——缺了模型就"忘了"自己调过工具；
2. 🔴 每个 tool_call 必须紧跟一条 `{"role":"tool","tool_call_id":id,"content":文本}`；
3. 🔴 并行多个 tool_calls 必须**全部执行、全部回复**；
4. 🟡 reasoning 字段：不同厂商的回传规则不同（有的必传、有的不能传），按厂商文档分支处理；
5. 🟡 流式 tool_calls 分片：`index` 分槽、id / name 只在首片、arguments 用 `+=` 累加。

**数据格式（人机一致）**：

- 🔴 人类可手改的库（记忆 / 词条）用**一行一条**的纯文本格式，程序只认固定行首标记；
  解析规则出现在多处时，**改格式必须同时改**；
- 🔴 过程流水（聊天记录）与沉淀事实（记忆库）**物理分开**；增删改查序号**从 1 开始**。

## 12 · 单文件结构（禁止巨型主函数）

> 逐帧管线 / 摄像头 / 传感器这类"主循环脚本"最容**易**烂成一坨：一个几百行的 main()
> 既开设备、又识别、又判断、又画图、又管按键。本节就是防这个的（由一次真实重构蒸馏）。

**🔴 巨型主函数禁令**：`main()` 只做**编排**——建对象、进循环、按顺序调用功能函数。
一个功能块要留在 main 里，必须能在 30 秒内说清它"吃什么、吐什么"；
说不清就拆成函数，函数超过一屏就拆成模块。

**🔴 单文件三段式**（用注释横幅分区，段与段之间是单向依赖）：

```text
① 判定逻辑    纯逻辑类：只吃数值/坐标/时间，不 import 设备、GUI、推理框架
② 设备与画面   打开设备、构建识别器、绘制文字与图形
③ 主流程 main  读帧 → 更新状态 → 画 → 按键（每帧一圈的目录）
```

① 不碰设备是铁律——它因此可以被合成数据离线单测（见 §08）；② 是①和③之间
唯一的硬件翻译层；③ 退化成一张"每帧做什么"的目录，肉眼扫一遍就知道流程。

**🔴 文件头注释必须包含结构**（三样，缺一不可）：

1. **函数结构树 / 分区导航**——文件分几段、每段有哪些函数；
2. **调用关系总览**——谁调用谁、哪些调用每帧执行、哪些只执行一次；
3. **数据流单行链路**——如：帧 → 关键点 → 指标 → 状态机 → 状态快照 → 屏幕。

**🔴 状态机封装成类**（"这一帧怎么判"取决于"之前发生了什么"的逻辑，禁止散装变量）：

- 状态（计数器、时间戳、布尔档位、阶段名）全部是**实例字段**；
- 对外窄接口只有 `update(now, 输入) → 状态快照` 与 `reset()`；
- reset 逻辑**只写一份**，构造时与"用户按重置键"共用——两处手抄必然漂移；
- **控制状态与显示状态分离**：给屏幕看的文字/颜色不参与任何判断；
- 🟡 **意图与执行两相**：动作函数只写"目标值"，另一个每帧执行的推进器把"当前值"
  沿缓动曲线向目标走——目标中途变了不用管。

**🟡 配套两条**：路径统一登记见 §02 路径地址簿（"统一路径区"）；跨文件同款的
叶子小函数在头部标注"与 X 同款，需同步修改"。

**🟡 快速自检**：把 main() 读一遍，如果需要滚动超过一屏、或者里面出现了
"打开设备""算指标""画框"混在同一层——就还欠一次拆分。

## 13 · The Zen of Python（总纲）

> Tim Peters 的这段禅是上面所有条款的"为什么"。逐条对照：每一条禅语
> 都能在本规范里找到落地条款——写代码拿不准时，先读禅，再读对照表。

```text
The Zen of Python, by Tim Peters

Beautiful is better than ugly.
Explicit is better than implicit.
Simple is better than complex.
Complex is better than complicated.
Flat is better than nested.
Sparse is better than dense.
Readability counts.
Special cases aren't special enough to break the rules.
Although practicality beats purity.
Errors should never pass silently.
Unless explicitly silenced.
In the face of ambiguity, refuse the temptation to guess.
There should be one-- and preferably only one --obvious way to do it.
Although that way may not be obvious at first unless you're Dutch.
Now is better than never.
Although never is often better than *right* now.
If the implementation is hard to explain, it's a bad idea.
If the implementation is easy to explain, it may be a good idea.
Namespaces are one honking great idea -- let's do more of those!
```

| 禅语 | 落到本规范 |
|---|---|
| Flat is better than nested | §12 禁止巨型主函数——拆函数、拆模块、分区横幅 |
| Readability counts | §09 注释与命名 + §12 文件头结构注释 |
| Explicit is better than implicit | §02 路径显式登记 + §05 返回契约（字段名即契约） |
| Errors should never pass silently | §06 错误处理哲学（除非显式吞掉并留痕） |
| There should be one -- and preferably only one -- obvious way to do it | §04 I/O 单一入口 + §02 路径地址簿（一个口子一种做法） |
| Simple is better than complex / Complex is better than complicated | §01 分层解耦——复杂问题拆成一层层简单的东西 |
| If the implementation is hard to explain, it's a bad idea | §12 的 30 秒法则：说不清"吃什么吐什么"的函数该拆 |
| Although practicality beats purity | §11 已固化教训——先锁住行为再议重构，别为了纯范顺手"修" |
| Now is better than never / never is often better than *right* now | 先声明再动手（工作流程 §05）；拍板之前不动代码 |
